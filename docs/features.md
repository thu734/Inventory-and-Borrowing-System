## Current catalog freshness status

At assessed staging `4cf4ee1` (27 November 2026), the stale-catalog path remains present in source. [EquipmentCatalog](../frontend/src/features/catalog/EquipmentCatalog.tsx) fetches `/assets` on mount and when its own Refresh Equipment counter changes. Successful checkout in [CustodianWorkspace](../frontend/src/features/custodian/CustodianWorkspace.tsx) refreshes only Custodian requests/Loans; [App](../frontend/src/app/App.tsx) provides no shared refresh signal. Loaded catalog cards therefore retain prior availability until explicit catalog refresh or remount; an already-open detail remains stale until reopened or cleared/refetched. No fix to this path appears between main baseline `e042f06` and the assessed candidate; the Lab 7 UI correction changes cancellation behavior/status styling instead.

[Catalog UI tests](../frontend/src/features/catalog/catalog.ui.test.tsx) cover initial availability and manual refresh; [Custodian UI tests](../frontend/src/features/custodian/custodian.ui.test.tsx) cover checkout and its own record refresh. Neither tests both components together. The [F-04 PostgreSQL test](../backend/tests/f04.postgres.test.ts) verifies a new catalog API read returns unavailable, which does not establish automatic UI refresh. The [historical browser evidence](sprints/sprint-1/evidence/Sprint-1-integration-verification.md) observed the stale card; this review inspected source/history and did not rerun that browser journey. This existing display defect is not resolved; it does not itself demonstrate a cancellation or database-integrity failure. Its impact is stale availability guidance until refresh. On 27 November 2026, the GCP owner/release coordinator explicitly accepted it as a known release limitation within that scope (see [release decision](labs/lab-07/release-safety.md#5-release-decision-and-remaining-gates)). A future fix requires catalog/checkout state synchronization and a combined UI regression test, tracked separately from this documentation change.
